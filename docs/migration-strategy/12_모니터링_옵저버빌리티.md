## 1. 프론트엔드 모니터링

### 1.1 Real User Monitoring (RUM)

실제 사용자 환경에서의 Web Vitals를 실시간으로 수집하여 사용자 경험을 정량적으로 측정한다.

| 지표 | 설명 | 목표값 |
|------|------|--------|
| LCP (Largest Contentful Paint) | 최대 콘텐츠 렌더링 시간 | < 1.5s (p95) |
| FID (First Input Delay) | 첫 입력 지연 시간 | < 100ms |
| CLS (Cumulative Layout Shift) | 누적 레이아웃 이동 | < 0.1 |
| INP (Interaction to Next Paint) | 상호작용 응답 시간 | < 200ms |
| TTFB (Time to First Byte) | 서버 응답 시간 | < 200ms |

**수집 방식:**

```typescript
// Next.js Web Vitals 리포팅
export function reportWebVitals(metric: NextWebVitalsMetric) {
  const body = {
    name: metric.name,
    value: metric.value,
    rating: metric.rating,
    delta: metric.delta,
    id: metric.id,
    page: window.location.pathname,
    userAgent: navigator.userAgent,
    timestamp: Date.now(),
  };

  // Beacon API로 비동기 전송
  navigator.sendBeacon('/api/vitals', JSON.stringify(body));
}
```

### 1.2 Error Tracking (Sentry)

소스맵 연동을 통해 프로덕션 환경의 에러를 원본 코드 위치로 매핑한다.

**설정 항목:**

- 소스맵 업로드: 빌드 시 자동 업로드 (CI/CD 파이프라인 연동)
- Release 태깅: Git 커밋 해시 기반 릴리스 추적
- 환경 구분: `production`, `staging`, `development`
- 사용자 컨텍스트: 로그인 사용자 ID, 역할 정보 포함
- 성능 트레이싱: 트랜잭션 샘플링 비율 설정 (프로덕션 10%, 스테이징 100%)

**에러 분류 기준:**

| 레벨 | 기준 | 대응 |
|------|------|------|
| Fatal | 앱 크래시, 렌더링 실패 | 즉시 알림 (P1) |
| Error | API 호출 실패, 예외 미처리 | 15분 내 알림 (P2) |
| Warning | 성능 저하, 폐기 예정 API 사용 | 일간 리포트 |
| Info | 사용자 행동 로그 | 주간 분석 |

### 1.3 Session Replay

사용자 세션을 녹화하여 실제 사용자 행동을 재현하고 UX 이슈를 진단한다.

**활용 시나리오:**

- 에러 발생 시 해당 세션 자동 캡처
- 전환율 저하 구간 사용자 행동 분석
- 비디오 플레이어 관련 이슈 재현
- A/B 테스트 사용자 행동 비교

**프라이버시 보호:**

- 비밀번호, 카드 번호 등 민감 필드 마스킹
- 개인정보 입력 영역 자동 차단
- 세션 데이터 보존 기간: 30일
- GDPR/개인정보보호법 준수 동의 기반 수집

## 2. 성능 모니터링

### 2.1 Core Web Vitals 대시보드

Grafana 기반의 실시간 대시보드를 구성하여 핵심 성능 지표를 모니터링한다.

**대시보드 구성:**

| 패널 | 내용 | 갱신 주기 |
|------|------|-----------|
| Web Vitals 추이 | LCP, FID, CLS, INP 시계열 | 1분 |
| 디바이스별 성능 | 모바일 vs 데스크톱 비교 | 5분 |
| 지역별 성능 | 국가/도시별 응답 시간 | 5분 |
| 에러율 추이 | JS 에러, API 에러 비율 | 1분 |
| 사용자 만족도 | Good / Needs Improvement / Poor 비율 | 5분 |

### 2.2 라우트별 성능 추적

Next.js의 각 라우트(페이지)별로 성능을 개별 추적한다.

**주요 추적 라우트:**

```
/                          → 랜딩 페이지
/dashboard                 → 대시보드
/learn/[courseId]           → 학습 페이지 (비디오 플레이어)
/learn/[courseId]/review    → 복습 페이지
/projects/[projectId]      → 프로젝트 상세
/admin/*                   → 관리자 페이지
```

**라우트별 성능 기준:**

| 라우트 유형 | LCP 목표 | TTFB 목표 | 비고 |
|-------------|----------|-----------|------|
| 정적 페이지 | < 1.0s | < 100ms | CDN 캐시 적용 |
| 동적 페이지 | < 1.5s | < 200ms | SSR/ISR 적용 |
| 비디오 페이지 | < 2.0s | < 300ms | 비디오 로딩 제외 |
| API 라우트 | N/A | < 100ms | JSON 응답 |

### 2.3 번들 크기 변화 추적 (PR별)

PR마다 번들 크기 변화를 자동으로 분석하고 리포트한다.

**CI/CD 연동:**

```yaml
# GitHub Actions 번들 분석
- name: Bundle Size Analysis
  run: |
    npx next build
    npx @next/bundle-analyzer

- name: Comment PR with Bundle Report
  uses: actions/github-script@v7
  with:
    script: |
      // 이전 빌드 대비 번들 크기 변화량 코멘트
```

**번들 크기 경고 기준:**

| 변화량 | 상태 | 대응 |
|--------|------|------|
| < 5KB 증가 | 정상 | 자동 승인 |
| 5KB ~ 20KB 증가 | 주의 | 리뷰어 확인 필요 |
| > 20KB 증가 | 경고 | 코드 분할/최적화 필수 |
| 감소 | 개선 | 자동 승인 |

## 3. 인프라 모니터링

### 3.1 GCP Cloud Monitoring

Google Cloud Platform의 네이티브 모니터링 서비스를 활용한다.

**모니터링 대상:**

```
GCP 프로젝트
├── Cloud Run (API 서버, 워커)
├── AlloyDB (PostgreSQL 호환)
├── Memorystore (Redis)
├── Cloud Storage (미디어 파일)
├── Cloud CDN (정적 자산)
├── Cloud Load Balancing
└── Cloud Tasks / Pub/Sub
```

### 3.2 Container 메트릭

Cloud Run 컨테이너의 핵심 메트릭을 수집하고 모니터링한다.

| 메트릭 | 설명 | 경고 임계값 | 위험 임계값 |
|--------|------|-------------|-------------|
| CPU 사용률 | 컨테이너 CPU 사용량 | > 70% (5분 지속) | > 90% (1분 지속) |
| 메모리 사용률 | 컨테이너 메모리 사용량 | > 80% | > 95% |
| 요청 수 | 초당 요청 수 (RPS) | > 1000 RPS | > 2000 RPS |
| 요청 지연 시간 | p50, p95, p99 응답 시간 | p99 > 500ms | p99 > 2s |
| 인스턴스 수 | 활성 컨테이너 인스턴스 | > 50 | > 100 |
| 콜드 스타트 빈도 | 신규 인스턴스 시작 비율 | > 10% | > 30% |
| 에러율 (5xx) | 서버 에러 비율 | > 0.5% | > 1% |

**오토스케일링 설정:**

```yaml
# Cloud Run 스케일링 설정
scaling:
  minInstances: 2          # 최소 인스턴스 (콜드 스타트 방지)
  maxInstances: 100        # 최대 인스턴스
  concurrency: 80          # 인스턴스당 동시 요청 수
  cpuThreshold: 70         # CPU 기반 스케일 아웃 임계값
```

### 3.3 PostgreSQL (AlloyDB) 모니터링

| 메트릭 | 설명 | 경고 임계값 |
|--------|------|-------------|
| 쿼리 실행 시간 | 슬로우 쿼리 탐지 | > 500ms |
| 연결 풀 사용률 | 활성 연결 수 / 최대 연결 수 | > 80% |
| 디스크 사용량 | 스토리지 사용률 | > 80% |
| 복제 지연 | 읽기 복제본 지연 시간 | > 1s |
| 트랜잭션 처리량 | TPS (Transactions Per Second) | 급격한 변화 |
| 데드락 빈도 | 데드락 발생 횟수 | > 0 |
| 캐시 히트율 | 버퍼 캐시 히트 비율 | < 95% |

**슬로우 쿼리 알림 설정:**

```sql
-- PostgreSQL 슬로우 쿼리 로깅 설정
ALTER SYSTEM SET log_min_duration_statement = 500;  -- 500ms 이상 쿼리 로깅
ALTER SYSTEM SET log_statement = 'mod';              -- DDL/DML 쿼리 로깅
ALTER SYSTEM SET shared_preload_libraries = 'pg_stat_statements';
```

### 3.4 Redis (Memorystore) 모니터링

| 메트릭 | 설명 | 경고 임계값 |
|--------|------|-------------|
| 캐시 히트율 | 히트 / (히트 + 미스) | < 90% |
| 메모리 사용량 | 전체 메모리 사용률 | > 80% |

| 키 만료율 | 만료된 키 비율 | 급격한 변화 |
| 명령 처리량 | 초당 명령 처리 수 | > 10,000 ops/s |
| 복제 지연 | 복제본 동기화 지연 | > 1s |

```json
    "projectId": "proj-456",

  }

```

### 4.2 GCP Cloud Logging

Cloud Logging을 활용한 중앙 집중식 로그 관리 체계를 구축한다.

**로그 라우팅 규칙:**

| 소스 | 로그 싱크 | 보존 기간 |
|------|-----------|-----------|
| 애플리케이션 로그 | Cloud Logging | 30일 |
| 에러 로그 (ERROR 이상) | Cloud Logging + BigQuery | 90일 |
| 감사 로그 (Admin Activity) | Cloud Logging + Cloud Storage | 1년 |
| 접근 로그 (Data Access) | Cloud Logging | 30일 |
| 보안 로그 | Cloud Logging + SIEM | 1년 |

**로그 필터 예시:**

```
# ERROR 이상 로그 필터
resource.type="cloud_run_revision"
severity >= ERROR
jsonPayload.service="api-server"

# 슬로우 쿼리 필터
resource.type="cloud_run_revision"
jsonPayload.duration > 1000
jsonPayload.path=~"/api/v1/.*"
```

### 4.3 로그 레벨별 알림 정책

| 로그 레벨 | 조건 | 알림 채널 | 대응 시간 |
|-----------|------|-----------|-----------|
| CRITICAL | 서비스 장애, 데이터 손실 위험 | PagerDuty + Slack + SMS | 즉시 |
| ERROR | 처리되지 않은 예외, API 실패 | PagerDuty + Slack | 15분 내 |
| WARNING | 성능 저하, 리소스 부족 징후 | Slack | 1시간 내 |
| INFO | 정상 운영 로그 | 대시보드 표시 | N/A |
| DEBUG | 디버깅 정보 (프로덕션 비활성) | N/A | N/A |

## 5. 알림 정책

### 5.1 우선순위별 알림 체계

#### P1 — 서비스 다운 (즉시 대응)

| 조건 | 알림 채널 | 에스컬레이션 |
|------|-----------|-------------|
| 서비스 전체 다운 (5xx > 50%) | Slack + SMS + 전화 | 5분 미응답 시 → 팀장 |
| 데이터베이스 접속 불가 | Slack + SMS + 전화 | 5분 미응답 시 → 팀장 |
| 인증 서비스 장애 | Slack + SMS | 10분 미응답 시 → 팀장 |
| 미디어 서비스 완전 중단 | Slack + SMS | 10분 미응답 시 → 팀장 |

#### P2 — 성능 저하 (5분 내 대응)

| 조건 | 알림 채널 | 에스컬레이션 |
|------|-----------|-------------|
| LCP > 2s (p95, 5분 지속) | Slack | 30분 미응답 시 → P1 격상 |
| API p99 > 1s (5분 지속) | Slack | 30분 미응답 시 → P1 격상 |
| CPU > 90% (5분 지속) | Slack | 15분 미응답 시 → P1 격상 |
| 메모리 > 95% | Slack | 즉시 → P1 격상 |

#### P3 — 에러율 증가 (15분 내 대응)

| 조건 | 알림 채널 | 에스컬레이션 |
|------|-----------|-------------|
| 에러율 > 1% (15분 지속) | Slack | 1시간 미응답 시 → P2 격상 |
| 캐시 히트율 < 80% | Slack | 다음 업무일 검토 |
| 슬로우 쿼리 > 10건/분 | Slack | 1시간 내 검토 |
| 디스크 사용량 > 85% | Slack | 24시간 내 조치 |

### 5.2 알림 채널 구성

```
알림 흐름:
모니터링 시스템
├── PagerDuty (P1/P2 온콜 관리)
│   ├── Slack #incidents 채널

│   └── #alerts-info (정보성)

    └── 일간/주간 리포트
```

### 5.3 온콜 로테이션

|------|------|
| 로테이션 주기 | 주간 교대 |

## 6. SLO / SLA

### 6.1 Service Level Objectives (SLO)

| 서비스 | SLO 지표 | 목표값 | 측정 기간 |
|--------|----------|--------|-----------|
| 전체 플랫폼 | 가용성 (Uptime) | 99.9% | 월간 |
| 웹 프론트엔드 | LCP p95 | < 1.5s | 주간 |
| 웹 프론트엔드 | CLS p95 | < 0.1 | 주간 |
| API 서버 | 응답 시간 p99 | < 500ms | 주간 |
| API 서버 | 에러율 (5xx) | < 0.1% | 일간 |
| 비디오 스트리밍 | 버퍼링 비율 | < 1% | 주간 |
| AI 처리 | 콘텐츠 생성 성공률 | > 95% | 주간 |
| 데이터베이스 | 쿼리 응답 p99 | < 100ms | 일간 |

### 6.2 에러 버짓 (Error Budget)

```
월간 에러 버짓 계산 (99.9% SLO 기준):
- 월간 총 시간: 30일 x 24시간 x 60분 = 43,200분
- 허용 다운타임: 43,200 x 0.1% = 43.2분/월
- 주간 허용 다운타임: 약 10.8분/주
```

**에러 버짓 소진 정책:**

| 소진율 | 조치 |
|--------|------|
| < 50% | 정상 배포 진행 |
| 50% ~ 75% | 배포 빈도 축소, 위험 변경 보류 |
| 75% ~ 100% | 신규 배포 중단, 안정화 집중 |
| > 100% | 긴급 안정화, 포스트모템 진행 |

### 6.3 SLA (Service Level Agreement)

외부 고객 대상 SLA 정의:

| 항목 | SLA 보장 |
|------|----------|
| 플랫폼 가용성 | 99.9% (월 43분 다운타임 허용) |
| 계획된 유지보수 | 사전 72시간 공지 |
| 장애 알림 | 감지 후 30분 내 공지 |
| P1 장애 복구 | 4시간 내 |
| P2 장애 복구 | 8시간 내 |
| 데이터 백업 | 일 1회, 30일 보존 |

### 7.2 도구별 역할

| 도구 | 역할 | 주요 기능 |
|------|------|-----------|
| **Grafana** | 통합 대시보드 | 메트릭 시각화, 알림 규칙 관리, 팀별 대시보드 |
| **Prometheus** | 메트릭 수집/저장 | 시계열 데이터 수집, PromQL 쿼리, 알림 규칙 |
| **Sentry** | 에러 트래킹 | 소스맵 연동, 세션 리플레이, 성능 트레이싱 |
| **PagerDuty** | 인시던트 관리 | 온콜 로테이션, 에스컬레이션, 인시던트 대응 |
| **Cloud Monitoring** | GCP 인프라 모니터링 | Cloud Run, AlloyDB, Redis 메트릭 |
| **Cloud Logging** | 로그 관리 | 구조화 로그, 로그 라우팅, BigQuery 연동 |
| **Cloud Trace** | 분산 추적 | 요청 추적, 지연 시간 분석, 서비스 간 호출 |

### 7.3 분산 추적 (Distributed Tracing)

OpenTelemetry 기반의 분산 추적 체계를 구축하여 서비스 간 요청 흐름을 추적한다.

```
사용자 요청 흐름 추적 예시:

[Browser] → [Cloud CDN] → [Cloud Run: Next.js] → [Cloud Run: FastAPI]
    │                            │                        │
    │ trace-id: abc123           │ span: ssr-render       │ span: api-handler
    │                            │ duration: 120ms        │ duration: 80ms
    │                            │                        │
    │                            │                   [AlloyDB]
    │                            │                   span: db-query
    │                            │                   duration: 15ms
    │                            │
    │                       [Redis Cache]
    │                       span: cache-lookup
    │                       duration: 2ms
```

## 8. 인시던트 대응 프로세스

### 8.1 인시던트 라이프사이클

```
감지 → 분류 → 대응 → 해결 → 포스트모템
 │       │       │       │        │
 │       │       │       │        └── 재발 방지책 수립
 │       │       │       └── 서비스 정상화 확인
 │       │       └── 담당자 배정, 조치 시작
 │       └── P1/P2/P3 우선순위 결정
 └── 자동 알림 또는 사용자 신고
```

### 8.2 포스트모템 템플릿

모든 P1/P2 인시던트에 대해 포스트모템을 작성한다.

| 항목 | 내용 |
|------|------|
| 인시던트 요약 | 영향 범위, 지속 시간 |
| 타임라인 | 감지 ~ 해결까지 상세 기록 |
| 근본 원인 | 기술적 원인 분석 |
| 영향도 | 영향받은 사용자 수, 매출 영향 |
| 조치 사항 | 즉시 조치 + 장기 개선 사항 |
| 교훈 | 잘한 점, 개선할 점 |
| 액션 아이템 | 담당자, 기한 포함 |
